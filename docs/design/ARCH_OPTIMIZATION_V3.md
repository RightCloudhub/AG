# 架构优化 V3：多智能体编排的目标与进度

对象是协作的 LLM 角色及其编排：路由、分诊、Fast Path、Planner、Executor、Critic、
Answer + 蕴含判定、需求登记表。第一批（§3）已实现并通过离线门禁；§4 为后续批次，
只定目标与验收。真实模型下的准确率、费用和 P95 **均未验证**，见 §5。

## 1. 现状基线

`reports/` 不入库，这里保留本轮引用的数字。

| 指标 | 数值 | 来源与限制 |
|---|---|---|
| 单次查询耗时 / LLM 调用 | 15.2–23.3 s；5–6 次；均值 3.76 s/次 | 2026-10-29 `reports/online_eval`，**n=5**、合成题、单一网关，只作量级参考 |
| 角色占比（上述样本） | Critic 占调用 46%、token 57%；Planner、Answer、判定各约 18% | 由步骤数推算，当时无逐角色记录 |
| Agentic P95 | 约 75–92 s（AC-4 目标 ≤8 s） | 2026-07 历史值；原始行已是 0 字节文件，无法复算，须重测 |
| 确定性结果可替代的比例 | 分诊完整解析关系链：G2 160/200、POC 13/31、改写集 125/240；离线 critic 可给确定结论：G2 360/390、POC 52/56 | 分析探针，仅限合成语料，真实语言下须重测 |
| 离线门禁 | POC 31/31（agentic、triage）、G2 200/200、probe 54/54、20/20 | 与 live 效果无关 |

调用链是串行的：k 节点的 agentic 查询固定为
`planner(STRONG) → k × critic(LIGHT) → answer(STRONG) → 判定(LIGHT)`，共 k+3 次，
并发只发生在检索层。按 3.76 s/次估算，8 s 预算只容得下约 2 次串行调用，所以 AC-4
不能靠微调达到，必须减少串行调用次数或换更快的模型。

## 2. 优化目标

| # | 目标 | 可度量的验收 |
|---|---|---|
| G1 | **时延与成本**：只在确定性结果不确定时才调 LLM | 角色保真替身上 agentic 平均串行调用 ≤2.5（基线约 4.95）；live 配对无显著准确率损失且 Agentic P95 降 ≥40%；AC-4（≤8 s / ≤3 s）仍是最终目标 |
| G2 | **编排正确**：计划是唯一的执行来源 | 每个计划节点恰好执行一次，或带原因报告；Critic 只判已执行节点；护栏总先于递归上限停止 |
| G3 | **失败语义一致**：任一角色失败都不丢已有证据 | 故障矩阵（角色 × 超时 / 5xx / 坏 JSON / 熔断 / 预算）：0 未处理异常，有证据时 0 个 429/503/504，结果带降级原因 |
| G4 | **计量可信**：预算能约束真实花费 | `cost` 与实际远程调用一致；单查询上限只有一个来源；并发下不超限 |
| G5 | **可观测与归因**：坏答案能定位到角色 | 每次调用有角色、耗时、token；单故障矩阵上归因正确率 ≥85%（基线 33%）；每条链有结构化停止原因 |
| G6 | **上下文与安全边界** | 判定所见不少于生成所见；检索内容一律按不可信数据隔离；无引用内容不会随答案返回；敏感文本不进遥测 |
| G7 | **可演进**：改一个角色不必动编排 | 角色声明集中（档位、重试、失败策略可配置）；LLM 路径控制流进入 CI |

## 3. 第一批：已交付

全部可离线验证。括号内是诊断编号。

| 项 | 改动 | 对行为的影响 |
|---|---|---|
| 跳过语义（ORCH-03、STATE-02、OBS-10）G2 | `advance_past_skipped` 在 executor 超步内越过不可运行节点：不耗 hop，不进 Critic，不覆盖上一步判定，不重复 SSE 帧；原因写入 `metadata.skipped_sub_questions`；全部跳过时仍检查预算与超时 | **离线**：3 条 `probe_negative` 的步骤数 2→1、hop_count 3→1（如不再去查 BrightLink 的 CEO），状态仍为 `no_answer`；`unexecuted_sub_questions` 不再包含被跳过的节点 |
| 递归上限（ORCH-08）G2 | `min_recursion_limit` 改为结构上界 `2×hops+10`，覆盖证据缺口节点、同 hop 兄弟节点和每轮的收尾访问；配置值 18 | 递归兜底只作最后防线；默认配置下不再可达 |
| 新查询重置（STATE-08）G2 | `initial_state` 设置全部通道 | 复用 thread 不再继承跳闸状态和预取结果；API 路径原本不受影响 |
| 上限单一来源（GOV-3）G4 | API / SSE / eval 的查询预算读取 `guardrails.max_llm_calls` 与 `max_tokens_per_query` | **live**：实际上限从硬编码的 20 次降为配置的 16 次 |
| 计量补全（GOV-4、CTX-03、OBS-01）G4 | 每个查询一个受计量客户端，覆盖工具规划和查询 embedding；聊天调用加锁预留后结算，embedding 在发送前检查 token 上限；成功 HTTP 响应即使内容校验失败也结算，取消释放未完成调用的预留；`cost.embed_calls` 入链 | **live**：工具规划占聊天调用预算，embedding 只占 token 预算，可能更早触顶；已支付响应始终结算，即使超出 token 上限；查询 embedding 进入磁盘缓存；链 schema 增加字段 |
| 逐角色记账（OBS-02）G5 | `LLMRole` + `role_scope`，`metadata.llm_by_role` 记录每个角色的调用、token、远程耗时、失败、解析失败 | 仅元数据；未用 LLM 的运行不增加键 |
| 进程级熔断（GOV-7）G3 | 按端点共享 `CircuitBreakerSet`，半开探测持有独占许可直到退出，取消释放许可，旧代请求的迟到结果不改变新状态；探测失败重新冷却，400/413/422 不计入；前置检查按实际档位；STRONG→LIGHT 降级记入 `degraded_channels` 与 `metadata.degraded_from`；`/healthz` 的 `llm_circuit`、`agr_llm_circuit_open` | **live**：熔断打开后后续查询不再付连接超时，也不再被缓存为正常答案；慢探测超过冷却时长也不会放行第二个探测 |
| 指标语义（OBS-07）G5 | `agr_queries_total` 单调增长；百分位取最近窗口；新增 `agr_query_latency_ms` 分路由直方图、`agr_llm_calls_total{role}`、`agr_llm_remote_ms_total{role}` | RUNBOOK 告警改用分路由直方图 |
| 数据最小化（OBS-08）G6 | `AGR_REDACTION_ENABLED` 真正接入日志与审计（此前没有生产调用方，开关无效）；span 只记 `question_chars`；删除 `llm_error_msg`，只留异常类型名 | 开启脱敏后审计行被脱敏，`query_id`、`metadata.tenant_id` 等定位键保留 |

**仍未解决的相关缺口**：`agr-run-cases --direct` 的 LLM 未接预算；缓存回放仍按真实调用计费
（A/B 依赖此口径，是否调整待决）；rerank 未计量；失败和超时的查询仍不进指标（V3-06）；
`otel_bridge` 硬编码 `insecure=True`；`index_pipeline` 把原始异常文本写入文档元数据。

## 5. 验证口径

- 代码改动必须通过 ruff、format、mypy、`check_code_metrics.py`、覆盖率 ≥80% 和离线下限。
- 结构性改动要求离线报告逐题一致（预测、路由、步骤、证据 id、工具序列、Critic 动作）；
  有差异的，逐条说明并附 `scripts/eval_compare.py` 配对结果。
- **第一批的离线通过不能说明 live 收益。** 上限从 20 降到 16、工具规划占预算、熔断共享
  都改变 live 行为，上线前需要在同图、同题、同缓存上做配对验证，重点看触顶率和准确率。
  当前没有可用的 live 预算，这项未做，已在 IMPORTANT.md 挂账。
- 文中的 G1 目标依赖 live 复测；§1 基线样本过小，不能用来宣称达标。

第一批已完成改动范围内的代码复核。补充回归覆盖 embedding token 耗尽、畸形响应的结算、
取消后的预算与探测许可释放、迟到请求与半开失败，以及全部节点跳过后的护栏检查。
最终命令、离线配对数字和 3 条预期行为差异见
[第一批验证记录](../../CHANGELOG.md#arch-v3-batch-1)。

## 6. 诊断来源与可信度

诊断按 9 个维度并行展开，每维配对抗复核，最后做完整性检查。其中 6 个维度
（编排、角色契约、上下文、状态、护栏预算、可观测）完成分析；**时延、执行器、状态对账
3 个维度的分析，以及全部对抗复核和完整性检查，因 API 限流未完成。** 因此：

- §3 每一项都由失败测试先行复现，再实现修复，属于已验证结论。
- 第一批代码复核与回归已完成；上述未完成的诊断维度和研究计数仍需补验。
- §4 中高严重度条目的代码事实已人工逐条核对；其中的计数（如归因 33%、4000 次模糊测试）
  来自分析探针，未被独立复现，立项时应先重测。
- 时延和执行器维度只被其他维度部分覆盖，后续应补做；可能还有未发现的问题。
